# VE 内存统计受控验证计划

效率目标仍有真实内存占用和权重常驻待实现。当前硬件/运行环境已通过原生VE运算与整图验证，温度监控持续可用；本机veosinfo3 3.6.0存在，开发头文件缺失。只读预探测前三个unsigned long字段返回48 GiB总量且使用+空闲等于总量，尚不足以宣称接口或峰值完成验收。

准备原生程序受控申请512 MiB、触碰每页并释放，用握手使主机在各阶段查询全节点内存。只读接口签名和字段前缀参考[SX-Aurora原始绑定](https://github.com/SX-Aurora/py-veosinfo/blob/49d517386e085ee3328f4548e9fadbd06c6aae26/veosinfo/_veosinfo.pyx)；自编适配代码使用额外大且对齐的输出缓冲，仅读取已验证的前三字段，限定本机已观测版本。该验证不替代完整头文件布局证明，也不验证其他接口。

编译和512MiB探测必须等六提示验证结束，单独温度守护、CPU占空比25%，不与模型测试并发。检查分配前后节点使用量增加至少512MiB且不超过额外32MiB对齐开销，释放后回到基线附近；同步记录原生sysconf/getrusage，以识别统计域，不假设主机/proc RSS等于VE HBM。失败就不将该接口作为权重常驻预算证据。

后续建立采样器，报告VEOS全节点已用内存的采样峰值、基线和间隔；不是单进程独占量，也不能保证抓到瞬态最大值。现在尚未编译/运行受控程序，不能声称HBM峰值测量完成。

## 首次探测未通过与修正

首次malloc申请512MiB后，节点计数准确增加524288 KiB；free后未下降，因此释放门禁失败，不能把该运行标成完整校准通过。原生sysconf报告64MiB页（768页组成48GiB），说明先前假定额外32MiB对齐窗口不适合本机。改用匿名mmap/munmap明确控制映射释放，允许至多一个实测页的辅助分配/对齐差，但仍要求大块映射解除后回落；不把保留512MiB的失败运行直接放宽为通过。同步交叉验证原生页数×页大小等于VEOS报告总量。CPU62°C、VE43.375°C，本轮没有温度问题。

## 延迟回收校准通过

第三次串行温度守护测试 `build/results/20261009T052956Z-ve-memory-calibration`：512 MiB触页申请使VEOS使用量准确增加512 MiB；munmap后即时仍多320 MiB，0.5秒后的20次采样全部恢复进程基线448 MiB。退出后10次采样全部恢复启动前节点基线128 MiB。原失败记录保留，未放宽释放阈值。CPU最高61°C，VE最高43°C，可读风扇状态无变化。只验证本机veosinfo3 3.6.0的前三个输出字段，不能据此声称已测模型HBM峰值。检测脚本随后仅改进即时/稳定释放值的命名与输出，已测报告保持原样。
