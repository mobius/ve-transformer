# SD-Turbo 连续节点内存测量

本轮环境检查：x86_64 96逻辑CPU、ASPEED显示设备、三张VE1；授权运行环境槽1/2/3设备及VEOS存在，实际执行仍须温度守护验收。上一轮im2col实际运行通过。veosinfo3 3.6.0只读输出前三字段经512MiB触页及延迟回收校准。

计划在温度守护内以0.2秒间隔采集槽1全节点内存，运行同一已验收二进制、固定单步参考、全部向量候选。采样失败或超时停止子进程组，失败记录保留。记录完整轨迹与查询间隔，公开摘要注明这是离散采样最高值，包括VEOS与其他进程，不能等同瞬时峰值或模型独占占用。

不修改原推理检查器/二进制，使数值和来源哈希沿用已验收路径。测量结果用于决定是否能同时保留三组件权重与最大工作区；常驻设计需明确生命周期、每请求工作区释放、重复请求数值一致和加载次数，不仅删除当前释放调用。

## 生命周期检查

当前CLIP和VAE的runner是函数栈对象，调用结束析构并释放权重；UNet已有open/run/close，四步共用权重但进程末尾关闭。仅把UNet关闭移走不会消除CLIP/VAE重复加载。生成overlay的GGMLRunner采用CPU+NLC调度器，CLIP/VAE每次compute释放调度器工作区，UNet保留用于同图多步。

候选设计：三个组件分别提供open/run/close，以RAII对象持有backend和runner；每请求新建32MiB输出工作区，返回数组已复制到该工作区。先按实际调用顺序懒加载一次，后续请求复用三组件权重；CLIP/VAE保持原调度器释放，UNet在请求末尾显式释放调度器，避免三份工作区叠加。保留按请求重载模式作同二进制对照。每请求输出独立目录和完整诊断，记录加载次数与请求耗时。两个请求以上验证第二请求不能串用前次数组/文本、四步和六提示后再给性能结论。

三组件各有阻塞型8线程池，多池不同时执行，但常驻会增加线程栈/metadata；节点连续采样必须覆盖第二请求和退出回收。官方权重总有效载荷4.805GiB不是实际常驻占用。当前固定验证入口不会宣称生产服务完成；常驻请求接口需实际验证后再推荐。

## 实际测量通过

槽1、同一已验收二进制、8线程常驻池+SiLU/Softmax/im2col ve，单提示单步五项独立CPU参考全部通过，进程91.357秒。未做性能对照，不能据此宣称新收益。全节点528次离散采样，目标间隔0.2秒、最大实际间隔0.20106秒；最高5,580,800 KiB（5.3223 GiB），启动和退出稳定基线均131,072 KiB（128 MiB）。当前不是三组件同时常驻；最高值不保证覆盖采样间的瞬时峰值。

实际runner权重缓冲：CLIP1346.53 MiB，UNet3303.19 MiB，VAE解码器188.79 MiB，合计4838.51 MiB；这是模型日志缓冲大小，不是官方三组件全部参数有效载荷。把本次整个节点采样最高值再加三份权重缓冲可作粗略保守空间估算约10.05 GiB，相对48 GiB有较大余量，但不构成常驻峰值证明，metadata、线程栈及内存保留需在候选中实测。

温度CPU最高72°C，VE最高49.5°C。97个可读状态/策略通道无变化；没有物理风扇转速/完整策略结论。完整轨迹及原始日志在忽略目录，公开摘要只含相对路径与筛选指标。
